LLM inference notes

Sampling → KV cache → the roofline model, in order

1. Decoding pipeline (logits → next token)

Logits→ Temperature scaling→ Softmax→ Top-k / Top-p filter→ Renormalize→ Multinomial sample

Temperature

Divides logits before softmax. Low T → sharper, more confident distribution. High T → flatter, more random/creative (sometimes nonsensical).

Top-k

Always keeps a fixed count of tokens (e.g. k=50), regardless of how peaked or flat the distribution is.

Top-p (nucleus sampling)

Sort probabilities descending, walk down accumulating them, stop as soon as the cumulative sum ≥ p. Keep that set — the count is dynamic, adapting to the shape of the distribution.

Example (p = 0.9):
the: 0.48 (cum 0.48) · a: 0.29 (cum 0.77) · cat: 0.11 (cum 0.88) · dog: 0.09 (cum 0.97 ← crosses 0.9, stop)
Keep {the, a, cat, dog}. Renormalize by dividing each by the total kept mass (0.97) — not by the crossing token's own probability — so they sum back to 1. Then sample.

2. KV cache

Self-attention needs a Key and Value vector for every token seen so far. Without a cache, you recompute K,V for the entire sequence from scratch at every generation step — pure waste, since nothing about past tokens changed.

StepWithout cacheWith cache
Predict token 5compute K,V for 4 tokenscompute K,V for 4 tokens
Predict token 6compute K,V for 5 tokenscompute K,V for 1 new token
Predict token 7compute K,V for 6 tokenscompute K,V for 1 new token
GrowthO(n²) — quadraticO(n) — linear

Cache is per-layer. Each transformer block has its own W_k, W_v, so each block's K,V are numerically different and must be cached separately. 8 layers → 8 independent KV caches. Total cache size ≈ layers × 2 (K,V) × tokens × dim.

3. The roofline model

A way to see whether an operation is bottlenecked by compute or by memory bandwidth, based on arithmetic intensity = compute ÷ bytes moved.

Memory-bound idle computeCompute-bound busy compute
Bytes moveda lotrelatively few
Compute per bytetinylarge
Position on rooflinebelow the diagonal (left)on the plateau (right, past the ridge)

Prefill vs decode

  • Prefill (processing the prompt): matrix-matrix multiply — one weight load reused across many tokens at once. High intensity → compute-bound.
  • Decode (one new token at a time, with KV cache): matrix-vector multiply — huge weights loaded, tiny compute for one token. Low intensity → memory-bound.
KV cache's effect on the roofline position:
Without cache, you redo real (wasted) matrix work every step — looks more compute-heavy, sits higher.
With cache, that recompute vanishes — what's left is almost pure memory movement vs. tiny compute. The point drops low and left, deep into memory-bound. The cache doesn't just save time — it exposes the true bottleneck.

4. The goal — and why so many techniques exist

The whole aim across LLM inference optimization: push arithmetic intensity up, cross the ridge point, keep the GPU's compute units busy instead of idle waiting on memory.

TechniqueHow it raises arithmetic intensity
Continuous / dynamic batchingone weight load now serves many requests' tokens, not one
Multi-query / grouped-query attentionshrinks KV cache size per token → less data to move
Speculative decodingverifies several draft tokens in one batched pass
Quantization (int8 / int4)fewer bytes per weight for the same compute
FlashAttentionavoids writing/reading large intermediates to slow memory
