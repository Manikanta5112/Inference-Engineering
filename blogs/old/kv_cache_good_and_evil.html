1. The waste hiding in the autoregressive loop

Every autoregressive language model generates text one token at a time. At each step, you take the sequence generated so far, run it through the model, and look at only the last row of the output to decide the next token.

Here's the part that's easy to miss the first time you see it: the naive implementation passes the entire sequence through the model at every single step — even though 99% of that computation produces numbers you already had from the previous step.

for step in range(30):
    outputs = model(input_ids)          # ← full forward pass on ALL tokens
    logits = outputs.logits
    next_token_logits = logits[:, -1, :]  # ← but we only use the LAST row
    next_token_id = next_token_logits.argmax(dim=-1)
    input_ids = torch.cat([input_ids, next_token_id], dim=-1)
The waste, concretely: starting from a 5-token prompt and generating 30 tokens, by the final step you're passing 35 tokens through an entire 7-billion-parameter model just to read off the logits for the last one. Every token before it gets recomputed from scratch — identically, every time.

This is what the KV cache fixes. Self-attention needs a Key and Value vector for every token in the sequence. Those vectors, once computed for a given token at a given layer, never change — they depend only on that token's embedding and the model weights, both of which are fixed. So instead of recomputing them, you cache them, and each new step only has to compute K and V for the one new token.

2. Measuring the speedup, for real

Theory is nice, but the numbers make it visceral. I benchmarked per-token decode latency on Qwen2.5-7B, with and without caching, across several starting context lengths — using CUDA events for GPU-accurate timing.

The pattern is the whole story: without caching, per-token latency climbs steadily as the sequence grows, because you're reprocessing more and more tokens at every step. With caching, latency stays essentially flat — each step only ever processes one new token, regardless of how long the conversation has gotten.

3. The dark side: a formula for how much memory you're spending

The speedup is bought with memory, and the exchange rate is steep. The KV cache has to store a Key and a Value vector — for every token, at every layer, for every attention head that isn't shared.

DeepSeek-V3 at 128K context needs 478 GB of KV cache for a single sequence — that's six H100 GPUs' worth of memory, before you've served a single other user. This exact number is why DeepSeek invented Multi-Head Latent Attention (MLA): the standard KV cache formula was simply unworkable at their target context length.

4. What this means for a real GPU's memory budget

On an actual GPU, memory is split between three things: model weights (fixed), KV cache (grows with context × batch size), and activations (small, temporary). The KV cache is the only one of these that scales with how many people you're serving and how long their conversations run — which makes it the thing that actually determines your serving capacity.

Model (H100 80GB)Available for KV cacheMax users @ 8K ctxMax users @ 128K ctx

Llama 3 70B (per-GPU, TP=4)43 GB17~1
Doubling the context length halves your max concurrent users. This is the direct, mechanical reason API providers charge more for larger context windows — the hardware cost is dominated by KV cache memory, not by the extra compute.

5. Production inference: vLLM, PagedAttention, and continuous batching

Production inference engines like vLLM always run with KV caching on — there's no toggle, because turning it off would mean O(T²) latency in production. What vLLM adds on top is PagedAttention (managing the KV cache like an OS manages virtual memory, so there's no fragmentation) and continuous batching (dynamically packing many requests' decode steps together).

Benchmarking Qwen2.5-7B through vLLM on the same H100, throughput scales dramatically with batch size — this is the payoff of turning many memory-bound, one-token-at-a-time decode steps into a shared, better-utilized batch:

Where this goes next: the entire field of "efficient attention variants" — MQA, GQA, MLA — exists to answer one question: how do we keep the speed of the KV cache without paying its full memory cost?
  • MQA (Multi-Query Attention) — share K, V across all heads → cache shrinks by a factor of n_heads
  • GQA (Grouped-Query Attention) — share K, V within groups of heads → a tunable dial between MHA's quality and MQA's memory savings
  • MLA (Multi-Head Latent Attention) — compress K, V into a shared low-rank latent space → the technique DeepSeek needed to make 128K context tractable at all
