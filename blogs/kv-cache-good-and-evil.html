The good and evil of KV cache

How one optimization gave transformers linear-time decoding — and quietly became the biggest memory bottleneck in LLM serving.
Benchmarked on Qwen2.5-7B · NVIDIA H100 80GB HBM3

1. The waste hiding in the autoregressive loop

Every autoregressive language model generates text one token at a time. At each step, you take the sequence generated so far, run it through the model, and look at only the last row of the output to decide the next token.

Here's the part that's easy to miss the first time you see it: the naive implementation passes the entire sequence through the model at every single step — even though 99% of that computation produces numbers you already had from the previous step.

for step in range(30):
    outputs = model(input_ids)          # ← full forward pass on ALL tokens
    logits = outputs.logits
    next_token_logits = logits[:, -1, :]  # ← but we only use the LAST row
    next_token_id = next_token_logits.argmax(dim=-1)
    input_ids = torch.cat([input_ids, next_token_id], dim=-1)
The waste, concretely: starting from a 5-token prompt and generating 30 tokens, by the final step you're passing 35 tokens through an entire 7-billion-parameter model just to read off the logits for the last one. Every token before it gets recomputed from scratch — identically, every time.

This is what the KV cache fixes. Self-attention needs a Key and Value vector for every token in the sequence. Those vectors, once computed for a given token at a given layer, never change — they depend only on that token's embedding and the model weights, both fixed. So instead of recomputing them, you cache them, and each new step only computes K and V for the one new token.

3. The dark side: a formula for how much memory you're spending

The speedup is bought with memory, and the exchange rate is steep. The KV cache has to store a Key and a Value vector — for every token, at every layer, for every attention head that isn't shared.

4. What this means for a real GPU's memory budget

On an actual GPU, memory splits between model weights (fixed), KV cache (grows with context × batch), and activations (small, temporary). The KV cache is the only one that scales with how many people you're serving — which makes it the thing that actually determines your serving capacity.

Doubling the context length halves your max concurrent users. This is the direct, mechanical reason API providers charge more for larger context windows — the hardware cost is dominated by KV cache memory, not by the extra compute.

5. Production inference: vLLM, PagedAttention & continuous batching

Production inference engines like vLLM always run with KV caching on — turning it off would mean O(T²) latency in production. What vLLM adds on top is PagedAttention (managing the KV cache like an OS manages virtual memory, so there's no fragmentation) and continuous batching (dynamically packing many requests' decode steps together).

Benchmarking Qwen2.5-7B through vLLM on the same H100, throughput scales sharply with batch size — this is the payoff of turning many memory-bound, one-token-at-a-time decode steps into a shared, better-utilized batch.

Where this goes next: the field of "efficient attention variants" — MQA, GQA, MLA — exists to answer one question: how do we keep the speed of the KV cache without paying its full memory cost?
  • MQA — share K, V across all heads → cache shrinks by a factor of n_heads
  • GQA — share K, V within groups of heads → a tunable dial between MHA's quality and MQA's memory savings
  • MLA — compress K, V into a shared low-rank latent space → the technique DeepSeek needed to make 128K context tractable at all
