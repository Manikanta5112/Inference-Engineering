The two faces of inference

Prefill reads your prompt all at once. Decode writes the reply one word at a time.

Same model, same weights, two completely different memory-bound stories. Watch what actually happens to the weight matrix in each phase.

01 - The full journey

One prompt, two phases

Say you type this prompt. The teal tokens all get processed together in one shot (prefill). Then the model starts producing the orange tokens, one at a time, each one depending on everything before it (decode).

ThecapitalofFranceis → Paris→ ,→ a→ city
Prefill

Read the prompt

All 5 input tokens go through the model together, as one batched matmul. This also builds the KV cache - a saved copy of each prompt token's Key/Value vectors, so decode never has to reprocess the prompt.

Decode

Write the reply

One new token at a time. Each step only needs to process that single new token - but still needs the entire weight matrix pulled in from HBM to do it.

02 - Watch prefill

One weight fetch, reused across every prompt token

Press run: the weight tile loads from HBM once, then all 5 prompt tokens pass through it while it's still sitting in fast memory. That's high reuse per byte fetched - compute-bound.

03 - Watch decode

One weight fetch, per single token, every time

Press run: for each new token, the same weight matrix has to make the full HBM trip again - used once, evicted, fetched again for the next token. That's minimal reuse per byte - memory-bound.

Ridge point for an H100-class chip (989 TFLOPs ÷ 3.35 TB/s) sits around 295 FLOPs/byte - prefill clears it easily, decode isn't remotely close.

05 - The fix

Batching drags decode toward compute-bound

If you batch multiple users' decode requests together, the matmul's n goes from 1 to the batch size. Same weight tile loaded once, but now reused across every request in the batch. Drag the slider - this is the exact lever inference servers (vLLM, TensorRT-LLM, etc.) pull.
